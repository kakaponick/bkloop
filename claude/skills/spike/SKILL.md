name: spike
description: Research an unknown before building on it — an undocumented API, a protocol, a file format, a third party's behaviour, an auth flow — by probing the live system with the real sessions, proxies and samples the user put in .spike/, and capture a cited findings doc in docs/ plus a reusable toolkit in .spike/toolkits/<topic>/. Use on /spike, when asked to investigate, reverse-engineer, verify or audit an external system, or when a task depends on facts no doc in the repo carries.
argument-hint: "<question>"
---

A **spike** is a time-boxed investigation that ends in facts, not product code: a doc a developer builds on and a toolkit the next spike starts from. The `spike-researcher` agent (`.claude/agents/`) does the work; you frame, launch and verify.

1. **Frame.** The question in the user's words. The deliverable: what will be built on the answer, hence what the doc must settle (transport, auth, envelopes, objects, limits, risks — or a format's layout, or a behaviour's exact rule). Prior art: the repo's findings docs and toolkits (`docs/api/*.md`, `docs/research/*.md`, `docs/*.md`, `.spike/toolkits/*/README.md`) — a doc that already answers part of it is named so the spike extends instead of repeating; the best of them is the **reference doc** whose shape the new one matches. Topic slug → the doc at `docs/api/<topic>.md` (an API) or `docs/research/<topic>.md` (anything else), the toolkit at `.spike/toolkits/<topic>/`.
2. **Resources.** `.spike/` in the repo root (gitignored) is the research workspace: `README.md` in their words at the root; shared data — proxies, samples, exports — in `.spike/data/`, what each thing is and any limits; each account in `.spike/sessions/<name>/` (anything that opens the account: session string, tdata, cookies, 2FA); under `.spike/toolkits/<topic>/` each investigation's own toolkit and probes. Read it; missing → say what to drop there and continue with the offline branches (the system's own code, docs). The README's limits are the only limits; none written → none.
3. **Lease.** An account is used by one process at a time — two clients on one session lose the auth key. Before the launch, `node .claude/skills/bkloop/spike-lease.mjs acquire <repo> <session>` for every session the question needs (busy → `--wait <s>`, or report who holds it); `release` after the report. In a plain checkout this only marks the lease; in a worktree it also links the folder in.
4. **Launch** `spike-researcher` (foreground, `model: opus`) with: `Repo:`, the question, the deliverable, prior art, the doc path and toolkit dir, the reference doc and toolkit or `none`, what `.spike/` holds and which sessions are leased. Several independent unknowns → one launch each, in one message, no two on one session.
5. **Verify the report.** Every ANSWERED line carries evidence (`live <date> <script>` or `source <file:line|url>`); a claim without one moves to UNVERIFIED before it reaches the summary. The doc exists at the path, the toolkit's README lists the gotchas hit. Nothing is committed — the doc is for the user to commit, the toolkit stays in `.spike/`.
6. **Notify.** `socket notify --topic spike/<topic> "<RESULT line + OPEN items>"` (skill `ai-socket`) — the developer may have left the terminal while the agent waited on them.
7. **Summary**, in the user's language: answered (claim → evidence) · unverified and why · risks (rate limits, anti-bot, owner notifications, geo) · what to add to `.spike/` for the next run · files.
